# Отчёт по проекту

## Общая идея проекта

Проект представляет собой Telegram-бота для обучения сотрудников с использованием LLM. Бот не просто задаёт тестовые вопросы, а ведёт пользователя по учебным разделам, отвечает на уточняющие вопросы, проводит мини-тест после каждого блока и сохраняет прогресс в PostgreSQL. Такой подход делает сценарий ближе к реальному обучению, а не к одноразовой проверке знаний.

## Архитектура и связи модулей

Корневой `main.py` отвечает только за запуск приложения через `asyncio.run()`. Основная инициализация находится в `bot/main.py`: там создаются `Bot`, `Dispatcher`, подключение к базе, сервис бизнес-логики и сервис общения с LLM. Модуль `bot/handlers/onboarding.py` управляет Telegram-сценарием: принимает `/start`, собирает имя сотрудника, показывает разделы, переводит к тесту, обрабатывает результаты и завершает сессию. Модуль `config/settings.py` читает настройки из `.env` и передаёт их остальным частям приложения. Модуль `services/training_service.py` реализует правила прохождения курса: разбор разделов, проверку порога прохождения, повторы и переходы между блоками. Модуль `services/ai_training_service.py` отправляет structured-запросы в LLM и возвращает типизированный ответ.

## Docker Compose и взаимодействие контейнеров

Проект запускается в двух контейнерах: `db` и `bot`. Контейнер `db` поднимает PostgreSQL, а контейнер `bot` собирается из локального исходного кода и использует `.env` для подключения к базе и LLM API. Параметр `healthcheck` нужен для проверки готовности PostgreSQL через `pg_isready`. Параметр `depends_on` с условием `service_healthy` нужен, чтобы бот не стартовал до тех пор, пока база действительно не начнёт принимать подключения. Параметр `volumes` сохраняет данные Postgres между перезапусками контейнеров. Для подключения с хоста используется внешний порт `55432`, чтобы не конфликтовать с локальным PostgreSQL.

## Логика обучения

Текущая версия проекта была переработана под тему **«Правила работы с клиентами»**. Учебный материал разбит на 5 крупных разделов, каждый из которых содержит самостоятельный блок знаний. После показа раздела пользователь может задавать вопросы по материалу. Когда он пишет `готов`, запускается мини-тест из 5 вопросов только по текущему блоку. Если результат `4/5` или выше, бот переводит сотрудника к следующему разделу. Если результат ниже порога, бот поддерживает пользователя, повторно показывает тот же материал и предлагает пройти тест заново.

## Почему используется async/await

Асинхронный подход в этом проекте особенно полезен, потому что бот постоянно работает с внешними I/O-операциями. Он получает сообщения из Telegram, отправляет HTTP-запросы в LLM API и выполняет запросы к PostgreSQL. `async/await` позволяет не блокировать весь процесс на каждом из таких ожиданий. Благодаря этому бот остаётся отзывчивым даже при медленном ответе модели или базы. Для Telegram-бота с сетевой логикой это естественный и правильный выбор.

## Почему PostgreSQL, а не SQLite

PostgreSQL лучше подходит для реального использования и развёртывания в Docker. Она поддерживает многопользовательскую работу, удобна для подключения внешних инструментов вроде DBeaver и лучше масштабируется под рост проекта. SQLite была бы удобна для простого локального прототипа, но хуже подходит для контейнерного сервиса с несколькими источниками доступа и накоплением аналитики по обучению. В текущем проекте важно хранить результаты по каждому разделу и видеть прогресс сотрудников, а PostgreSQL для этого подходит значительно лучше.
